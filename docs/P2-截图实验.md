## 1. 实验设置

| 项 | 内容 |
| --- | --- |
| 样本 | 3 张真实截图（微信支付账单列表 / 微信支付单笔详情 / 第三方记账 App 明细页） |
| 基准答案 | 人工逐字读图确定，不是模型输出 |
| 路线 A | 图 → `deepseek-flash`（多模态）一步直读 → tool call 结构化 |
| 路线 B1 | 图 → `deepseek-flash` 转写成文本 → `deepseek-chat` 走**产品文本管线** → 结构化 |
| 路线 B2 | 图 → `deepseek-ai/DeepSeek-OCR`（硅基流动，3B 限免）转写 → 同上（**D2 §6.3 的原意**） |
| 共用 | 同一份工具定义、同一个产品 `StructuredExtractor`（上限 2 次，含修正型重试）、同一套判据 |
| 判分字段 | 金额（分，严格相等）、商户（归一后相等/包含）、方向、笔数；**时间只记录不判分** |

判分只看四列、且以金额与商户为主，是沿用 D2 §6.3 的判断：它们是"错一个字就变成另一个数/另一个人"的字段。
时间不自动判分，是因为图上的时间可能是分组标签、相对词或带秒的绝对时间，自动比对只会引入误差。

### 三点说明（都在 `p2-experiment/README.md` 有记录）

1. **B1 是 B2 的备胎**：先没有硅基流动 Key，才用通用视觉模型顶替转写器；补上 Key 后两者都跑。
   两者结构完全相同、只换转写器——**这顺带演示了 B 路线"OCR 可替换"这件事**（决策 40 留的两条退路）。
2. 路线 A 必须带 `thinking:{"type":"disabled"}`（原因见 §3.5）。
3. 实验里 `paymentMethod` 放宽成字符串（产品里是枚举），避免措辞不匹配触发重试、淹没正题。

## 3. 关键发现

### 3.1 多笔截图：可做，且已纳入 P2 范围

三张图里两张是多笔（s1 两笔、s3 六笔）。**多数情况下模型能数对**：A 与 B1 两张都报对，
B2 在账单列表上报对、在记账明细上报错（见 §3.3），笔数合计 8/9。

**用户已定：P2 做"一图多笔"**（`HANDOFF` 决策 41）——一张截图产出多张草稿。

实现上它需要动 `llm-client` 的工具定义结构：现在的 `ToolSchema.Builder` 只支持扁平字段，
产不出"账目数组"，这是 P2 已知的最大改动面。好消息是 `t_draft` 的 `batchId` / `splitIndex`
两列 P1 就留好了（决策 14 埋的），**落库不需要改 schema**。

### 3.2 账单列表页的「时间标签」会挂错

s1 里 `昨天 21:09` 这个标签夹在两张卡片之间，**两条路线都把它给了上面那笔**（邓三姐）。
而 s2 显示发丝缘那笔的转账时间正是 `2026年10月02日 21:09:26`——按微信账单的语义，
这个标签属于**下面**那笔。
即：列表页类的版面，模型对"时间标签属于哪一条记录"存在系统性误判。
单笔详情页（s2）没有这个问题。

### 3.3 转写文本的质量与「格式副作用」

**金额与符号都保住了**：三条路线的转写都保留了 `¥7.00`、`-15.00`、`-100.00` 这类原文，
以及商户名、支付方式、订单号；**没有出现"金额被读错"这条路线 B 的死穴**——
但样本量太小，不能据此认定它不会发生。

**但 DeepSeek-OCR 的输出风格带来一个新问题**：它按"文档理解"的习惯输出 **Markdown**
（`# 记账本` / `#### 转账` / `**-100.00**`），而 B1 的通用视觉模型输出的是平铺文本
（`转账 -100.00` / `18:34 | 转账-转给Felicity.`）。后果在下游才显形：

- B2 在记账明细图上把 `transactionCount` 报成 **1**（B1 与 A 都报对 6）——
  Markdown 的层级让它把整页读成"一份文档"而不是"六条并列记录"
- B2 在账单列表图上也漏掉了 `昨天 21:09`（同样是分组标签被当成了标题）

**这是 P2 实现阶段必须处理的一环**：转写那一环要明确要求"逐条平铺、不要 Markdown 层级"，
或在结构化那一步把版面提示写得更硬。**换 OCR 模型不只是换一个字符串，还要连输出风格一起收住。**

### 3.4 枚举只给末级路径，会白重试一次

本轮 9 次解析里的 **3 次重试原因完全相同**（A / B1 / B2 在 s3 上各一次）：模型第一次给了 `categoryPath: "人情"`（一级），
而枚举里只有末级路径（`人情>红包` / `人情>礼物` / `人情>请客`），schema 校验直接打回，
模型第二次改成 `人情>红包` 才通过。

**这个坑产品里同样存在**：`DraftToolSchema` 的枚举来自 `tree.selectable(...)`，也只给末级。
文字入口罕见"只报一级"，但转账默认落「人情」是一级，所以截图/转账场景容易撞上。
两道可选修法：

| 方案 | 改动 | 代价 |
| --- | --- | --- |
| 把一级也放进枚举 | `DraftToolSchema` 生成处加一级路径 | 分类候选可能挂一级；报表按一级聚合，不影响数字 |
| prompt/schema 描述里写明"必须给末级路径" | 改一段文案 | 零结构改动，但靠模型自觉 |

顺带：**这三次重试恰好证明了产品容错设计的价值**——修正型重试把三次即将降级的解析都救了回来，
是答辩里可以讲的实证（不是"设计得很完善"，而是"它真的救回来了三次"）。

### 3.5 模型侧新限制：V4 系列默认思考模式，不接受"指定函数"的 tool_choice

实测矩阵（`p2-experiment/tools/tool-choice-probe.ps1` 可复现）：

| 请求形状 | 结果 |
| --- | --- |
| `deepseek-chat` + 指定函数（**产品当前形状**） | ✅ 正常 |
| `deepseek-chat` + `tool_choice:"required"` | ✅ 正常 |
| `deepseek-v4-pro` / `deepseek-flash` + 指定函数 | ❌ `400 Thinking mode does not support this tool_choice` |
| `deepseek-flash` + `thinking:{"type":"disabled"}` + 指定函数 | ✅ 正常 |
| `deepseek-flash` + 指定函数 + `reasoning_effort:"low"` | ❌ 同样 400（压低思考档位不等于关掉） |
| `deepseek-flash` + 不指定 tool_choice | ✅ 但**模型不调工具**，退化成正文回答 |

结论两条：

1. **产品主链没坏**：`LlmProvider.DEEPSEEK` 的默认模型仍是 `deepseek-chat`，它接受产品现有的写法。
2. **一旦把模型换成 V4 系列，`OpenAiCompatibleLlmClient` 必须补 `thinking:disabled`**，
   否则 function calling 直接 400——而"不指定 tool_choice"不是退路（模型不发 tool_calls）。

## 4. 结论（**已定：路线 B**）

**用户 2026-10-04 拍板走路线 B**（`HANDOFF` 决策 40），依据是它与"多入口 + 统一管线"的核心判断一致：

| 维度 | 路线 A 多模态直读 | 路线 B 转写 + 文本管线（**选定**） |
| --- | --- | --- |
| 准确率（本轮） | 金额/方向 9/9 | 同左；笔数上 B2 有一处失手（§3.3） |
| 延迟 | 1.0–1.8 s | 2.1–4.0 s |
| 产品改动面 | `llm-client` 加多模态内容块（≈20 行）+ 处理 thinking 限制 | 转写产物就是文本，直接进 `ChatDraftParser` |
| 可解释性 | 止于最终 JSON | **转写文本可留档**，多了"它当时看到了什么"这一层证据 |
| 换模型成本 | 换模型即换全部行为 | **只换 OCR 那一步** |
| 金额鲁棒性 | 模型直接读图 | 多一道转写，理论上是新的出错点（本轮未出现） |

多花一次调用、多等一两秒，换来的是"统一管线 + 可解释 + 可换 OCR"；记账场景对延迟不敏感
（解析在后台跑，用户不会盯着看）。

**转写器的选择**：默认 `deepseek-ai/DeepSeek-OCR`（3B、限免、8K 上下文），
`deepseek-flash` 作为备胎——两者本实验都跑过，切换只改一个字符串。
注意 B2 的 Markdown 输出风格必须在 prompt 里收住（§3.3）。

**遗留的共同前提**：时间归属要在实现时处理（§3.2）；多笔已立项（§3.1）。
