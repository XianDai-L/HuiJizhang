## 2. 语言与 UI 方案：为什么是 Java + XML

### 2.1 决定性的判据是「答辩可解释性」

毕设评的是「你做出了一个完整的东西，**并且能解释清楚**」，不是「你用了多新的技术」。写一堆自己讲不出所以然的代码，答辩被追问两句就完了。

这一点上 Kotlin + Compose 有三处具体风险——「会用」和「懂原理」差着一整个身位：

- **协程的 `suspend` 怎么实现的**（编译器 CPS 变换、生成状态机）→ 被问「为什么不用线程」就卡住
- **Compose 的重组（recomposition）机制** → 为什么加 `remember`、`LaunchedEffect` 与 `SideEffect` 差在哪
- **空安全在字节码层面怎么落地** → `String?` 编译后仍靠注解与编译器检查

### 2.2 硬约束：Compose 只能用 Kotlin

`@Composable` 是 Kotlin 编译器插件能力，**没有 Java API**。所以「用 Java」意味着必须放弃 Compose，走 XML + View。

### 2.3 关键区分：要换的不是语言，是工程范式

两条路**都必须换写法**（教材那套撑不起本项目），区别只在换什么：

| | Kotlin 路线 | **Java 路线（采用）** |
| --- | --- | --- |
| 要学的东西 | **语言 + 范式**：Kotlin 语法、Compose 声明式 UI、协程 | **只有库的用法**：Room、ViewModel、RecyclerView、OkHttp |
| 底层还是熟悉的吗 | 否，是新体系 | **是**：Room 底层是 SQLite、ViewModel 底层是生命周期+观察者、OkHttp 底层是 Socket+线程池 |
| 学习量 | Kotlin 语法 1–2 天 + Compose 1–2 周 + 协程 1–3 天 | **约 1 周，全部是 API 记忆** |

### 2.4 必须避开的不是 Java，是「教材写法」

反面参照（一个常见的教学示例工程）：

| 教材写法（禁止） | 现代写法（采用） |
| --- | --- |
| `SQLiteOpenHelper` + 字符串拼 SQL（SQL 注入、单引号崩溃） | **Room**（编译期校验 + 参数绑定） |
| `onUpgrade` 空实现（加字段后无法迁移） | **Room Migration** |
| 单例静态持有 Activity context（内存泄漏） | **ViewModel** 持有数据，Activity 只做展示 |
| 业务逻辑全塞 `onCreate` | **分层**：Activity / ViewModel / Repository / DAO |
| 直接持有 `Cursor` 遍历 | **Room 返回实体列表** |

### 2.5 附带结论：`money-parser` 用 Java 重写完成

金额解析模块已从 Kotlin 重写为 Java，**74 条用例（JUnit 4）全部通过**，且输出与 Kotlin 版逐字一致。

*答辩可用叙事*：先用 Kotlin 快速写原型验证规则，规则定稿后用 Java 重写落地，并用同一套 74 条用例做回归验证，保证行为完全一致。这是真实的开发过程，也是「原型验证 → 移植 → 回归测试」的标准实践。

### 2.6 Java 版本要求

- `money-parser` 编译到 **Java 17** 字节码
- **因此 `app` 模块也必须 target Java 17**（否则 Gradle 会因 JVM 版本属性不匹配而构建失败）
- 整合 Android 工程时由我设置，不需要手工改
- Java 17 的 **text blocks**（`"""`）用于编写多行 prompt，避免 `\n` 拼接

## 3. 要不要后端

| 方案 | 说明 | 工作量 | 遗留问题 |
| --- | --- | --- | --- |
| **a. 纯客户端直连**（采用） | App 直接调大模型 API | 最小 | **API Key 打包在客户端，可被逆向提取** |
| b. 极薄代理 | 只做 Key 转发 + 限流，约 100 行 | 小 | 需要部署、域名与 HTTPS |
| c. 完整后端 | 账号 / 同步 / 鉴权全套 | 大 | 与毕设创新点无关 |

**采用 a，但网络层抽象成 `LlmClient` 接口。**

理由：

- 后端唯一实际作用是藏 Key。本项目已砍掉多用户，不需要账号、同步、鉴权
- 抽象接口成本为 0，却让「换成 b」只改一个实现类
- 答辩叙事：主动说明「单用户场景下 API Key 存于本地，若产品化则需服务端代理，代码中已预留抽象层」

## 4. 分层架构与目录结构

```
WiseBook/
├── settings.gradle.kts            多模块根（建 Android 工程后整合，见 §10）
├── build.gradle.kts
├── money-parser/                  ← 已完成：金额解析与双通道校验，不依赖 Android
│   └── src/main/java/com/wisebook/money/
├── llm-client/                    ← 已完成：模型调用与结构化输出容错，不依赖 Android
│   └── src/main/java/com/wisebook/llm/
└── app/                           ← Android 应用（骨架已建）
    └── src/main/java/com/wisebook/app/
        ├── input/                 输入入口（每种入口一个解析器）
        │   ├── voice/             录音 → ASR → 文本
        │   ├── image/             选图 → OCR/多模态
        │   ├── chat/              对话输入
        │   └── notification/      通知监听（P4）
        ├── domain/
        │   ├── draft/             草稿状态机（DRAFT / ASKING / …）
        │   ├── classify/          分类判定（模型给的分类 → 兜底桶，两段）
        │   └── confirm/           确认档位判定
        ├── data/
        │   ├── local/             Room：t_draft / t_entry / t_category / t_setting
        │   └── remote/            LlmClient 接口 + OpenAI 兼容实现
        └── ui/                    Activity / Fragment / Adapter
            ├── chat/              对话与反问
            ├── confirm/           确认页
            ├── ledger/            账本列表
            └── report/            报表
```

**核心架构约束（源自 D1）：所有入口只产出「草稿」，统一交给 `domain` 层。**
新增一个入口 = 新增一个 `input/` 下的解析器，`domain` 与 `data` 零改动。

**纯 JVM 模块的价值**：`money-parser`（以及后续可能的 `llm-client`）不依赖 Android，可脱离手机快速迭代——不用启模拟器、不用装 APK，改一行跑一次几秒钟。

## 5. 数据存储

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 引擎 | Room + SQLite | 本地优先、离线可用、隐私叙事 |
| 表结构 | 直接映射 D1 双表 | `t_draft` = 草稿，`t_entry` = 账目 |
| 金额类型 | `long`（分） | 记账铁律，禁止浮点 |
| 分类树 | `parent_id` 自引用 + `root_category_id` 冗余 | 支撑分类方案零迁移切换 |
| 迁移 | 必须实现 `Migration` | 教材那套空 `onUpgrade` 不可用，本项目会频繁加字段 |
| 云同步 | **不做** | 单用户；作为论文"未来工作" |
| 加密 | **不做**（SQLCipher） | 单机自用收益低，引入额外依赖与复杂度 |

## 6. 大模型选型与成本

### 6.1 需要的能力

1. 中文口语文本 → 结构化账目（**必须支持 function calling / JSON Schema 强约束**）
2. 中文账单截图 → 结构化
3. 稳定的结构化输出

### 6.2 已具备的接入条件

| 通道 | 接入 | 说明 |
| --- | --- | --- |
| 文本 | 硅基流动 `Qwen/Qwen3.6-35B-A3B` | 35B 总参 / 3B 激活的 MoE，带 `Tools` + `视觉` + 256K |
| 文本（对照实验） | 硅基流动 `Qwen/Qwen3.8-27B` | 最新，27B 密集模型，比 MoE 稳但更贵 |
| 截图 OCR 路线 | 硅基流动 `deepseek-ai/DeepSeek-OCR` | 3B、限免、专做文档理解。**仅 8K 上下文，长截图需切分** |
| 退路 | DeepSeek 官方 | 聚合平台限流时的备用链路 |

两家都是 **OpenAI 兼容协议**（`https://api.siliconflow.cn/v1`、`https://api.deepseek.com`），因此 `LlmClient` 只需**一套实现 + 一张配置表**（baseUrl / apiKey / modelName）。

**顺带收益**：换模型只改一个字符串，因此「多模型对比实验」几乎零成本——这正是论文实验章节的素材。D1 的 `t_draft.model` 字段（记模型名+版本）正好支撑这一点。

### 6.3 截图通道：两条路线，实验待定

| | 路线 A：多模态直读 | 路线 B：OCR + 文本管线 |
| --- | --- | --- |
| 流程 | 图 → 模型 → 结构化（一步） | 图 → OCR 文本 → 文本模型 → 结构化（两步） |
| 架构 | 截图是独立通道，需单独设计 prompt/schema/容错 | **截图退化为「文本来源」，与语音、对话复用同一条管线** |
| 成本 | 图占大量 token | OCR 3B 且限免 |
| 风险 | 长上下文下 JSON 易不完整 | OCR 读错金额则全错 |

**路线 B 架构上更优雅**（让 D1 的「多入口 + 统一管线」真正成立），但**金额符号的鲁棒性**是关键风险点。

**决定方式**：P2 开工前，取 30 张真实微信/支付宝截图，两条路都跑，比对金额与商户识别准确率。属于「实验待定」，不阻塞 P1。

### 6.4 成本结论（不依赖单价）

单用户记账场景的月调用量在 **数百次量级**。在这个量级上，**任何主流模型的总成本都在每月几元以内，可以忽略**。该结论只依赖调用量、不依赖单价，不会因价格波动失效。

**真正的成本不是钱，是调试期试错与限频。** 省钱关键也不是把多模态降级成 OCR，而是：

- 断言式规则能定的（金额校验器、时间解析、去重键）**不调模型**
- 相同输入做缓存
- 只在必要时调用（长截图先切分再逐段解析，避免整图重试）

### 6.5 必须提示的风险：涨价与限频

公开信息显示 2026 年出现过多轮**涨价、限购、限频、限场景**。对本项目的实际影响不是成本，而是：

- 开发调试期间可能被限流，拖慢进度
- **答辩演示当天若被限流，是现场事故**

**对策：**

1. **演示前准备离线降级路径**：`LlmClient` 提供一个「录制回放」实现，用真实响应预置数据跑通全流程，演示时不依赖网络
2. 已具备**两个厂商冗余**（硅基流动 + DeepSeek 官方），非同一条链路，可切换
3. 优先用限免/有赠额的模型（如 `DeepSeek-OCR` 当前限免）

### 6.6 已知实现风险

硅基流动**兼容 OpenAI Function Calling 格式，但在长上下文下偶发 JSON 格式不完整**。

这直接印证了 D1 定下的防线不是过度设计：
**function calling 强约束 → 输出后 schema 校验 → 失败重试一次 → 再失败降级为手动填写表单**。

注意其诱因是「长上下文」，而截图场景（图片 token 多）正好撞上，属高发区。此条建议写入论文的「容错设计」部分。

### 6.7 已实测的接口行为（2026-09-24，非推测）

用测试用例「今天打车28块」对两家真实端点各调用一次，结果：

| 观察项 | 结果 |
| --- | --- |
| `tool_choice` 指定具体函数（`{"type":"function","function":{"name":"..."}}`） | ✅ 两家都接受，未报 400 |
| `tool_calls[0].function.arguments` 结构 | ✅ 与 OpenAI 完全一致，且是 JSON **字符串**（需再解析一次） |
| 首次尝试即通过 | ✅ 2/2 |
| 返回内容 | 两家均为 `{"amountCents":2800,"direction":"expense","merchant":"打车"}` |

**顺带发现一个语义问题（比上面三条都重要）：**

两家都把 `merchant` 填成了「打车」—— 一个**动作**，而不是商户名。结构上完全合法：
类型是 string、字段可选、schema 全部通过、金额也对，**但语义是错的**。

这印证了一件事：**纯 schema 校验只能守住结构，守不住语义**。
D1 里「双通道校验」的定位是**只守金额那道防线**，不是万能药。

对应修法（P1 写 prompt 时必须加上）：

> `merchant` 只填具体的商户、平台或对方名称（如「滴滴」「星巴克」「张三」）；
> 不要把动作、品类填进来；无法确定时留空。

如果 prompt 收紧后仍有此类输出，则需要增加一层语义抽查——但那是 P1 之后的事。

## 7. 各输入入口的实现路径

| 入口 | 阶段 | 实现方式 | 关键点 |
| --- | --- | --- | --- |
| 对话 | **P1** | XML 界面 + `LlmClient` | 最先做，用来验证整条管线 |
| 截图 | P2 | `ActivityResultContracts.PickVisualMedia` | 长截图需切分；A/B 路线实验定 |
| 语音 | P3 | `SpeechRecognizer` → 文本 → 复用文本管线 | 出现「四/十」风险标记（见 D1 §2.3） |
| 通知监听 | P4 | `NotificationListenerService` | 应用内不能直接申请权限，须跳系统设置页并给图文引导 |
| 账单导入 | P4 | SAF 选 CSV → 解析 → 去重 | 官方唯一可行的"自动记账"路径 |

**重要：先做对话入口。** 它不涉及录音、摄像头、系统权限中的任何一个，却能验证「输入 → 解析 → 双通道校验 → 草稿状态机 → 确认 → 落账 → 报表」这条主链。主链跑通后再加入口，每个入口只换"解析器"。

## 8. 关键风险与对策

| 风险 | 对策 |
| --- | --- |
| 通知监听权限难申请 | 应用内无法直接申请，必须跳系统设置页 + 图文引导；前台服务保活 |
| 系统 ASR 识别率一般 | P3 先用系统 ASR（免费），不行再换云 ASR —— 管线不变，只换实现 |
| 长截图解析不稳 | 限制单次张数 + 失败转手动填写 |
| `DeepSeek-OCR` 仅 8K 上下文 | 账单列表长截图必须切分 |
| 无网络 | 解析失败 → 手动填写表单（状态机已支持） |
| API Key 泄露 | `LlmClient` 抽象层，为将来换代理留口 |
| 模型输出非 JSON | function calling 强约束 + schema 校验 + 重试一次 + 降级手动填写（D1 已定） |
| 演示当天限流 | 预置「录制回放」实现（见 §6.5） |
| 分类判错 | 报表按一级聚合，二级选错不影响统计；用户可随时改正（D1-A §4） |
| Room 迁移缺失导致数据丢失 | 必须实现 `Migration`，禁止空 `onUpgrade` |
