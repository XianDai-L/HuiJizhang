### 2.2 分类习惯学习

> ⏸ **本轮暂缓**（2026-10-04 用户决定，见 `HANDOFF` 决策 38）：先不做这类收益不确定的事。
> 下面的规格与三个设计点**留作将来参考**，不是被否掉了。

**规格**：D1 §6.4 第 5 条「用户改正过的『商户→分类』写入映射表。P1 只做记录，P2 启用。」
**现状**：**P1 一行都没做**，理由记在 HANDOFF 决策 23——四表 schema 里**没有**这张表，
`MerchantMap` 是**代码里的静态表**（42 条垂直映射 + 11 条平台规则，`VERSION = 1`），
要做「记录」得加一张表 + 一版 v2→v3 迁移，而记录下来的数据 P1 又不用，属于"为将来埋一张空表"。

**P2 要做的是三件事**：
1. 加表（用户改正记录）→ **v2→v3 迁移**（迁移必须真写，禁止 `fallbackToDestructiveMigration`）
2. 用户改正分类时（`EntryRepository.correctCategory`）写入这张表
3. `CategoryClassifier` 的第一层从「只查静态表」改为「**先查用户习惯表，再查静态表**」

**这里有两个设计点值得先想清楚**（都该写进注释，答辩时也会被问）：

1. **优先级**：习惯表命中即定，**优先于静态映射表、也优先于模型给的分类**。
   理由是"学习"这个词本身的含义——同一个人第二次把同一家店记成同一个分类，
   不该再问第二遍。这与现有三层判定的顺序（映射表 → 平台型规则 → 模型）是同一种思路：
   **越确定的越靠前**。
2. **理由要能追溯**：`CategoryClassifier.Result.reason` 会被展示在账目详情页上，
   习惯表命中时要写成「你上次把它记成 X」而不是一句"映射表命中"——
   用户得能分清**这是 AI 的判断，还是他自己以前的选择**（决策 31 已经在做这件事）。
   顺带：这行字也是排查"它为什么学歪了"的唯一线索。

## 5. 硬约束（别踩，每条都有理由）

| 约束 | 理由 / 位置 |
| --- | --- |
| **全项目 Java 17 + XML + View**，禁止 Kotlin、禁止 Compose | 用户 Java 熟练、Kotlin 不熟；答辩要能讲。D2 §2 |
| **金额一律 `long` 存「分」**，禁止浮点 | 浮点会产生 `0.1+0.2≠0.3`，累计成报表误差。D1 §3.6 |
| **`minSdk 26`**：禁用 `List.of` / `Set.of` / `List.copyOf` / `String.isBlank()` | 它们分别是 API 30 / 31 / 33 才有的，老设备会 `NoSuchMethodError` 崩溃。**三道防线都看不见它**（单测跑 JDK、模拟器是 API 36、Lint 不覆盖 `java.util` 集合工厂）。等价写法见 HANDOFF §8-21。<br>⚠️ 当心：你（AI）的练习代码很容易顺手写 `List.of`，**这条要主动自查** |
| Room `Migration` 必须真写，禁止 `fallbackToDestructiveMigration` | 空实现意味着只能卸载重装。`WiseBookDatabase` 里已有注释禁止 |
| 迁移里写了 `DEFAULT x`，实体上就必须写 `@ColumnInfo(defaultValue = "x")` | Room 会逐列比对（含默认值），不一致直接报错。HANDOFF §8-17 |
| 领域层**直接用 `DraftEntity` / `CategoryEntity`**，不另造模型互转 | 两套模型的互转代码没有业务含义，却会引入"漏映射字段"的静默 bug。HANDOFF 决策 10 |
| **不要信模型自报的置信度分数** | 它报的 0.9 经常是错的。用确定性判据。D1-A §4 |
| 模型输出非 JSON **是常态**（长上下文下高发） | 截图正好撞上这个场景。`StructuredExtractor` 已有「schema 校验 + 带错误反馈的重试 + 降级」，**直接复用**；那条"重试时把上次错误回传"的行为有测试守着，别改掉 |
| 产品代码只写 `WiseBook/` 内；AI 产物（文档/脚本/截图）只放 `WiseBook/` 外 | `AGENTS.md`。**唯一例外是 `WiseBook/AGENTS.md`，且它只是指路文件、内容不得扩张** |
| 临时文件任务结束就删 | `AGENTS.md` §三-5 |

## 7. 验收方式

1. **JVM 单测 + instrumented 必须全绿**（改动涉及数据库时要单独确认 `MigrationTest`）。
2. **界面改完必须装到模拟器上看一张图**——这条不是形式主义，P1 期间它抓到了三个
   测试和 Lint 都抓不到的 bug（金额格式同屏不一致、弹框分类"未定"、**键盘盖住输入栏**）。
   最后一个是"manifest 里 `adjustResize` 明明写着却不生效"（HANDOFF §8-29）——

## 9. 协作方式（重要，与 AGENTS.md 一致）

- 用户是**大四学生，Java 熟练、Kotlin 不熟**。**答辩优先原则：能讲清楚 > 技术新颖。**
  写代码时想一句"这段他能不能在答辩时讲出来"，讲不出原理的花哨写法宁可不写。
- **每个非显然的设计都要留一句理由**（代码注释保持这个密度，但不要写废话注释）。
  现有代码的中文注释都在解释"**为什么**这么做"，跟着这个风格走。
- **方案先行**：任何改动先给方案，等用户说「允许实施」再动文件。讨论阶段只分析。
- **不要替用户拍板关键决策**，列取舍让他选；但也不要问琐碎问题——低风险、可逆、
  用户已明确的事直接做。
- 沟通偏好：直接指出问题并解释原因，不要情绪包装；信息不足先停下来问。
- **用户会拿真机实测并把结果发回来**（P1 期间他报的每一条都是真问题：
  支付方式必填导致每笔都要确认、转账口径、模型把转账判成「其他」）。
  收到实机反馈时，**先复现、再定位、再改**，不要凭猜测直接改。
