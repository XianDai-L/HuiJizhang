## 3. 项目一句话

**慧记 WiseBook** —— 安卓记账 App（本科毕设）。通过**对话 / 截图 / 语音**三种入口记账，
AI 把非结构化信息转成结构化「账目草稿」，用户按档位确认后落账。
后续扩展：读付款通知、账单文件导入。

核心判断（全程贯穿）：**多入口 + 统一解析管线 + 统一账本**。
所有入口只产出"草稿"，之后的校验、去重、确认、落账全部复用。

### P1 新增决策（2026-09-24，滚动记录）

| # | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 设置存哪 | 用 Room 表 `t_setting`，**不用 DataStore** | D1 §3.5 已定稿该表，HANDOFF §6 也列为 P1 四表之一；D2 §1/§5 的「DataStore Preferences」与本清单冲突，以前者为准。已从 `app/build.gradle.kts` 移除未使用的 datastore 依赖 |
| 2 | API Key | `local.properties` → `BuildConfig` 作默认值，设置页可运行时覆盖 | HANDOFF §9 + 演示容灾（换 Key 免重编译） |
| 3 | `t_category` 缺收支方向 | 加 `direction` 列（一级存值；二级为 `NULL`，方向由父级继承） | D1-A §1 把一级明确分成支出 10 项 / 收入 6 项，但 D1 §3.4 的列清单漏了这一列。不补则分类选择器无法按收支分组、模型的分类枚举也无法按方向过滤（一笔支出可能被填成「工资」） |
| 4 | `t_entry` 缺「自动落账」标记 | 加 `auto_posted` 列 | D1 §5.3 要求自动落账的账目带视觉标记，但 §3.3 的列无从区分；而 §4 状态图显示两条路都走 `CONFIRMED → POSTED`，草稿状态也区分不了 |
| 5 | 迁移落地方式 | **v1 = D1 §3.2/§3.3/§3.4 逐字实现；v2 补上述两列（含收入分类回填）** | 让这条迁移成为真实开发过程的产物，而不是为演示而生造字段；且含「加列 + 数据回填」两步 |
| 6 | 默认确认档位 | 大额确认（阈值 300 元） | D1 未指定默认档位。取三档居中，答辩演示时两条路径都能走到 |
| 7 | 默认分类方案 | 标准（二级） | D1-A §2 的二级清单已定稿，说明它是主推形态 |
| 8 | `category_candidates` 不存 `score` | 只存 `{id, name}` | D1 §3.2 写的是 `{id, score}`，但 D1-A §4 明令「不使用候选分值分差阈值——模型自报分值不可靠」。既然判据不看，存下来只会被误用 |
| 9 | `EXPIRED` 的语义 | 停止自动流转，但**仍可由用户接管或丢弃** | D1 §4 状态图把它标成「终态」，§4.3 却要求「转待处理列表、不删除、由用户自行处理」，两者张力。按 §4.3 的意图处理，`POSTED` / `DISCARDED` 才是真终态 |
| 10 | 领域层是否另造一套模型 | **直接用 `DraftEntity` / `CategoryEntity`**，不做 entity ↔ 领域模型互转 | D1 定稿的 schema 就是领域模型。两套模型之间的互转代码没有业务含义，却会引入「漏映射某个字段」的静默 bug——而这里判错的后果是「该问的没问」。实体只是带注解的普通 Java 对象，不依赖 Android 运行时，所以领域层仍可在 JVM 上单测（P1-1 的 93 条就是证据） |
| 11 | D1-A §4 模糊词里的「点」 | 先按字面实现，**误报率待实测** | 「点」作为子串会误伤「酒店」「早点」，后果是多问用户一次（安全但不必要）。若实测误报偏多，收紧为「点了 / 点个」这类动宾形式 |
| 12 | 状态迁移建模 | 用**动作**（`DraftTransition`）而不是「状态对」 | 同一状态对可能对应不同意图：`POSTED` 既可能被「撤销」也可能被「改正」。用状态对无法区分，日志里也看不出用户干了什么 |
| 13 | Java API 兼容写法 | 全项目不用 `List.of` / `Set.of` / `List.copyOf` / `String.isBlank`，改用 `Collections` + `Arrays` 的等价写法 | 见 §8-21：它们分别是 API 30 / 31 / 33 才有的，而 minSdk 是 26。保持 minSdk 26（D2 §1 定稿）不动，代价只是写法啰嗦一点 |
| 14 | 多笔输入怎么处理 | P1 **只识别「多笔」并强制确认，不做自动拆分** | D1 §1.3 要求「拆分为多张草稿」，但拆分边界是模型最易出错处。P1 让模型只报 `transactionCount`，>1 就打 `SPLIT_UNCERTAIN` 强制走确认页，拆分交给用户。真正的自动拆分需要数组结构的工具定义（要动 `llm-client` 的 Builder），留作后续 |
| 15 | `confidence_flags` 的产出范围 | P1 只产出 `AMOUNT_AMBIGUOUS` / `CATEGORY_SWING` / `SPLIT_UNCERTAIN` | 标签是**全量事实记录**（论文统计要用），所以该打就打；`MISSING_FIELD` 由 `ConfirmPolicy` 直接检查实体并说明缺哪个字段，重复打标只会让确认页出现两句同义提示，故 P1 不打；`ASR_RISK` 属语音入口（P3）。**去重这件事放在「生成解释文案」那一步做**，不靠少打标来省 |
| 16 | 幂等落账放在哪一阶段 | **提前到 P1-3**（原计划在 P1-4） | 「免确认直落」按定义就是"解析完立刻入账"。若把它留到下一阶段，草稿会停在 `CONFIRMED` 这个悬空状态——既没入账、又不在待处理列表里，等于石沉大海 |
| 17 | `DRAFT` 状态会不会落库 | **不会**，它在 P1 里是瞬时状态 | D1 §4 的流程是「DRAFT 一触发确认条件就转 ASKING」，也就是解析完立刻按档位判定去向，落库时写的已经是 `ASKING` 或 `POSTED`。查询里保留 `status='draft'` 的条件不是 bug，是为了将来手动填表路径能复用它 |
| 18 | 设置页的 API Key 存哪 | SharedPreferences（`wisebook_llm_credentials`），**不进 `t_setting`** | 它是运行时凭证，不是领域设置。不进 `t_setting` 就不必改 D1 §3.5 定稿的列；也不用为一个 Key 引入 DataStore（决策 1 已定设置统一走 Room）。预填时只填"运行时覆盖值"，不填编译期默认值——否则一进设置页点保存就把 `local.properties` 的值固化成覆盖记录 |

## 8. 已踩过的坑（别重踩）

### 构建类

1. **`money-parser` / `llm-client` 编译到 Java 17 字节码** → `app` 必须也是 Java 17。
   降到 11 会因 Gradle 的 JVM 版本属性不匹配而构建失败。
2. **子模块不能有独立的 `settings.gradle.kts`** —— 会被 Gradle 认成独立工程。
   （上一轮已删除 `money-parser/settings.gradle.kts`）
3. 根工程启用了 `dependencyResolutionManagement { repositoriesMode = FAIL_ON_PROJECT_REPOS }`
   → **子模块不得写 `repositories {}`**，否则构建直接报错。仓库统一由根工程提供。
4. **Gradle 的 `System.getenv` 在配置期不可靠**（读到的是守护进程的环境）。
   不要用它在 build script 里转发 API Key —— 取不到会返回 null，若写成 `?: ""`
   就会把测试进程的真实环境变量**静默覆盖成空串**。上一轮删掉了这么一行。
5. **Gradle 按输入哈希判定 up-to-date**：改完再改回原样，测试任务会被跳过并显示
   `UP-TO-DATE`，看不到真实结果。要看结果用：
   - `:模块:cleanTest :模块:test` 强制重跑，或
   - 直接读 `模块/build/test-results/test/*.xml`

### 设计类

6. **不要用教材那套写数据库**：`SQLiteOpenHelper` + 字符串拼 SQL + 空 `onUpgrade`
   + 业务逻辑全塞 `onCreate`。用 **Room**，并且 **`onUpgrade`/`Migration` 必须实现** ——
   这个项目会频繁加字段，空实现意味着只能卸载重装。
7. **金额一律 `long` 存「分」**。浮点会产生 `0.1+0.2≠0.3`，累计成报表误差。
8. **不要信模型自报的置信度分数**（它报的 0.9 经常是错的）。用**确定性判据**：
   金额双通道校验、分类判定的前两层都是这个思路。
9. **模型输出非 JSON / 被截断是常态**，不是理论风险（硅基流动在长上下文下的已知问题）。
   `llm-client` 的 `StructuredExtractor` 已经处理了，**直接复用，不要再写一套**。
10. **纯 schema 校验管不了语义**。实测两家模型都把 `merchant` 填成「打车」（动作而非商户名）——
    结构合法、schema 全过，但语义是错的。prompt 必须收紧：
    > `merchant` 只填具体的商户、平台或对方名称（如「滴滴」「星巴克」「张三」）；
    > 不要把动作、品类填进来；无法确定时留空。

21. ⚠️ **`minSdk 26` 与 Java 9+ API 的冲突（P1-2 发现，此前三个模块全部中招）**

    | 调用 | 最低 API | 依据 |
    | --- | --- | --- |
    | `List.of` / `Set.of` / `Map.of` | **30** | `platforms/android-36.1/data/api-versions.xml` 的 `since` 属性 |
    | `List.copyOf` | **31** | 同上 |
    | `String.isBlank()` | **33** | 同上 |

    在 minSdk 26 上用它们，老设备上会 `NoSuchMethodError` 崩溃。

    **最要命的是三道防线全都看不见它：**
    - `app/src/test` 的单测跑在 **JDK** 上，Java 9+ API 当然都有
    - instrumented 测试跑在 **API 36** 的模拟器上，也都有
    - **Lint 的 `NewApi` 不覆盖 `java.util` 的集合工厂**（实测 `:app:lintDebug` 报 0 errors、7 warnings，全是版本过旧与未用资源）

    也就是说，只有真机是 API 26–29 时才会炸，而且是在运行时才炸。

    → **全项目统一改用 API 26 安全的等价写法**：

    ```
    List.of()      → Collections.emptyList()
    List.of(a, b)  → Collections.unmodifiableList(Arrays.asList(a, b))
    List.copyOf(x) → Collections.unmodifiableList(new ArrayList<>(x))
    Set.of(...)    → Collections.unmodifiableSet(new LinkedHashSet<>(Arrays.asList(...)))
    isBlank()      → trim().isEmpty()
    ```

    已替换：`app` 17 处、`llm-client` 6 处、`money-parser` 2 处。
    **`app/src/test` 与 `androidTest` 里的同类用法不用改**（测试环境本来就有这些 API）。

22. **`EdgeToEdge` 的 insets 回调里 `setPadding()` 是整体覆盖，不是累加。**

    模板生成的写法是
    ```java
    v.setPadding(bars.left, bars.top, bars.right, bars.bottom);
    ```
    它作用在没有 XML padding 的容器上没问题。但一旦容器自己写了
    `android:padding="24dp"`，那 24dp 就会被**悄悄抹掉**——表现是文字顶到屏幕边缘、
    长文本贴着边被裁。三个页面都中招。
    → 统一走 `ui/EdgeToEdgeInsets.apply(view)`：先记下原始 padding，再与系统栏尺寸相加。

    **这个 bug 值得单独记一笔，因为它是"看出来的"：** JVM 单测碰不到布局，
    `ActivityScenario` 冒烟测试只能证明页面能起来、控件找得到，
    Lint 也不管这种事。真正发现它靠的是**装到模拟器上截一张图**。
    界面代码改完之后，这一步别省。

23. **`DraftRepository.persist` 必须区分「新草稿插入」与「已有草稿更新」。**

    它的调用方有两个：解析管线（草稿还没有 id，要 insert）与确认页的
    「改完重新校验」（草稿是从库里读出来的，**已经有 id**，必须 update）。
    `autoPost` 一开始无条件走 `insert`，于是「用户把大额改小 → 重新校验 → 条件满足自动落账」
    这条路会直接撞主键：`SQLiteConstraintException: UNIQUE constraint failed: t_draft.draft_id`。

    这个 bug 是**写完 instrumented 测试跑出来的**，不是想出来的——
    `editsThatSatisfyTheConditionsAutoPost` 一跑就崩。现在两条路统一走 `saveOrInsert`。
    换句话说：**这类"同一条代码被两个入口复用"的地方，必须有测试分别覆盖两个入口**。

24. **instrumented 测试可能比 `Application` 的异步初始化先跑，从而偶发失败。**

    `WiseBookApp.onCreate` 里把「播种分类」「初始化设置」放进了后台线程，这是对的
    （磁盘操作不该占主线程）。但测试若依赖播种结果，就有个**竞态**：
    `UiSmokeTest.ledgerAndReportRenderPostedEntries` 需要分类树才能造账目，
    而分类树在应用刚起来时可能还是空的。

    **跑整套没暴露它，单独跑那一条才暴露**——因为跑整套时前面的用例已经把应用"热身"过了。
    这类"只有隔离运行才失败"的偶发问题，靠跑全套是抓不到的。

    修法是让测试自己**显式确保前置条件**（调用 `categoryRepository().ensureSeeded()`），
    而不是假设应用已经初始化好。**测试不应该依赖"前面跑过别的测试"。**

25. **`money-parser` 解析不了没有单位的小数金额（`283.4`）。**

    实机报「我买游戏花了283.4」每次都要确认。取真实调用日志看到：
    模型给的 `amountCents = 28340` **是对的**，但 `amount_rule_check = NA`、
    `confidenceFlags = [AMOUNT_AMBIGUOUS]`，还是反问「这笔具体是多少钱」。

    根因在 `AmountParser.tokenize`：数字扫描只认数字与中文数字，
    碰到 `.` 直接 `return null`，整段解析失败 → `RuleUnparseable` → 双通道校验对
    **最常见的一类写法**（带小数点）完全失效。

    修法是把小数拆成「283 元」+「4 角」两个 token，直接复用原有的元/角/分累加，
    不给 `Token` 加"小数位"字段——多一条并行折算路径就多一处可能算出不同结果的地方。

    **教训**：parser 的"解析不了"要区分「真的没法解析」与「我没实现这种写法」。
    前者该转人工确认，后者是 bug。这次的代价是每一笔小数金额都白问一次。

26. **确认页的「保存修改并重新校验」曾经是一张万能通行证。**

    用户报：「283.4 第一次要确认，点一下保存重新校验就过了，为什么两次判断不一致」。
    查下来 `ConfirmViewModel.syncEdits` 只要输入框能解析出金额，就无条件把
    `amountRuleCheck` 改成 `PASS`、并清掉 `AMOUNT_AMBIGUOUS`——
    用户**一个字都没改**，双通道校验的结论就被抹掉了。

    现在的判据是「值真的变了才算人工核过」，并且抽成静态方法配了单测。
    「我知道金额有疑问但就这样记」有专门的按钮（「确认并记账」），
    不该和「我改好了请重新判」混成同一个动作。

27. **测试不要依赖别处的默认值，也不要依赖环境。**

    这一轮同时踩到两次：
    - 默认档位从「大额确认」改成「存疑才确认」后，`DraftRepositoryTest` 里 7 条用例变红
      ——它们其实一条都没坏，只是"碰巧"建立在"默认值恰好是大额确认"之上。
      改成用 `largeModeSettings()` 显式设定档位。
    - 在 `local.properties` 配上 Key 之后，「没有 Key 时应提示去配置」那条用例变红
      ——它的前提没了。改成用 `assumeTrue` 把前提写明。

    判断标准：**用例的每一分前提，都应该能在用例里读到**——
    要么自己设，要么显式跳过。依赖别处的默认值，等于把别人的改动变成你的故障。

28. **「看起来能用、实际没接线」的控件是最难发现的一类 bug。**

    报表页的「排除转账」勾选框，实机上勾了会变色、文案也会跟着变，**但数字一个字不动**
    ——因为 `MonthlyReport.of` 里转账是无条件 `continue` 掉的，
    `includeTransfer` 只被用来选了一句提示文案。

    它躲过了全部测试，原因值得记：单测直接调 `MonthlyReport.of(..., includeTransfer)`，
    断言的是它被正确**传下去并保存**（`report.includeTransfer == false`），
    天然不会发现"这个参数对数字没有任何影响"。

    **判断标准：一个控件的存在，必须有它改变的东西。** 如果一个状态参数从头到尾
    只影响文案，那它要么该接线、要么该删掉——否则它比没有这个控件更糟：
    用户会以为自己已经控制了什么。写这类开关时，顺手问一句
    "把它拨到另一边，哪个数字会变？"答不上来就是接线还差一段。

29. **`windowSoftInputMode="adjustResize"` 在全面屏（edge-to-edge）下不生效。**

    首页输入栏做完之后，点开输入框：**键盘把输入栏整个盖住了**。
    而 manifest 里明明写着 `adjustResize`——这就是它难发现的地方：
    **配置本身是对的，是配置被别的东西架空了。**

    原因：`EdgeToEdge.enable()` 内部会调 `setDecorFitsSystemWindows(false)`，
    从那以后系统不再替窗口让出键盘的位置，IME 直接盖在内容上，
    `adjustResize` 变成一句空话（API 30+ 的行为）。

    修法是把键盘也当成一条"系统栏"来避让：
    `windowInsets.getInsets(systemBars() | ime())` 的底部自然取两者中较大的那个。
    并且**只在 API 30+ 加 `ime()`**——更早的版本系统不派发 IME insets，
    androidx 是用"窗口被压扁了多少"倒推的，而那时 `adjustResize` 又确实在生效，
    两边一起算会多出一整个键盘高度的空白。

    **这条值得单独记一笔，因为它只在真机/模拟器上、且只在键盘弹起时出现**：
    JVM 单测碰不到布局，`ActivityScenario` 冒烟测试里也没人弹键盘。
    又一次印证了那句话——**界面改完必须看一张图，而且要看"键盘弹起时"的那张**。

    答辩时可以直接拿这条讲（不是"设计得完善"，而是"它真的救回来过一次"）。

    测试：`DraftToolSchemaTest.categoryEnumIsStandardSchemeLastLevelPlusTopLevelsWithChildren`、

    ⚠️ 真机复核方法：说一句「转账5块」，看浮层第二行——**修好后应当是「模型调用 1 次，首次就通过」**；

33. **OCR 的 Markdown 输出会削弱「多笔」语义——用确定性归一化解决，而不是再问模型一次**（P2 实测）

    `DeepSeek-OCR` 按"文档理解"的习惯输出 Markdown（`# 记账本` / `#### 转账` / `**-100.00**`），
    下游文本模型会把这种层级读成"一份文档"而不是"六条并列记录"，
    **在记账明细图上把 6 笔报成 1 笔**（换用通用视觉模型输出平铺文本时没这个问题）。

    产品侧的解法是 `input/image/ImageTranscriptNormalizer`：剥掉层级标题与强调记号，
    但**保留金额的负号与小数点**——所以行首的 `-` 只在后面跟空白时才当列表符号，
    否则 `-100.00` 会被吃掉一个字符，而"金额从这里开始错"是最贵的错法。

    选择确定性代码而不是"再求模型一次"的理由：多一次调用就多一次不确定性，
    而"剥记号"这件事根本不需要理解语义。

    → 通用教训：**换模型不只是换一个字符串，输出风格也要一起收住。**

34. **`connectedDebugAndroidTest` 之后应用数据会被清掉**（P1 已知，P2 又踩一次）

    随后跑 instrumented 测试，测试结束应用数据被清空。
    所以"手动跑一遍 → 跑测试 → 再截图"这个顺序注定要重做第一步；

    确认页的同类控件当初调了（`applyRawState()` 在 `onCreate` 里），详情页漏了。
    **与 §8-23 是同一个形状：一段逻辑被两处复用，只做对了一处。**

    → 查这类问题的办法：**uiautomator dump 比看截图可靠**。截图里"看不见"可能是错觉
    （分辨率、缩放、我以为是我以为），而 dump 出来的 `text=` 是确定的事实，

    36. **界面改版后 `UiSmokeTest` 引用的 id 全失效，导致整个 androidTest 源集编译不过**（2026-10-08 实测，同日已修）

    37. **首页结果浮层"相邻两次同文案就不弹"**（2026-10-08 用户实机反馈，**同日已修**）

    `MainActivity.showResult` 拿**文案**当去重键：`summary + "|" + detail`，键相同就直接 `return`。
    本意是挡"转屏时 LiveData 把最后一条状态重放回来"（那个判断本身是对的），
    但有几类结果的文案是**常量**，于是"两笔一样的账"被错当成"状态重放"：

    | 场景 | 文案 | 后果 |
    | --- | --- | --- |
    | 免确认直落 | 「已自动记账」+「小额、无存疑、未重复，按当前档位直接入账。可在账本里核对或撤销」 | **连着记两笔能直落的账，第二笔浮层不弹**（最常见的触发场景） |
    | 解析失败 | 「没解析出来，请手动填写」+ 同一句降级原因 | 连着失败两次，第二次静默 |
    | 需要确认 | 「已生成草稿，等你确认」+ 同一条原因（例如两笔都缺金额） | 第二次静默 |

    用户的现象描述是"有时候解析对话内容时不显示浮层"——**不是时间冷却，是文案去重**。

    **用户给的三组实测（把机制钉死了，比任何代码推演都有说服力）**：

    | 实测 | 两次结果的文案 | 第二句 |
    | --- | --- | --- |
    | 「转账5块」→「转账6块」 | 都直落、调用次数也相同 → 一字不差 | 静默 |
    | 「转账5块」→「今天花了五块」 | 落点不同（或调用次数不同：转账句在吃 §8-31 那次重试） | 弹出 |
    | 「今天花了五块」→「今天花了六块」 | 都直落、都 1 次调用 → 一字不差 | 静默 |

    ✅ **修法（用户同意后做）**：去重键从"文案"换成**对象身份**——
    `if (state == lastShownState) return;`（`MainActivity` 一个字段 + 两行判断）。
    LiveData 重放给新观察者的是**同一个实例**（转屏挡得住），每次解析结果都是
    `UiState.result(...)` **新建的对象**（两笔一样的账也照样弹）。
    一句话：这条判断该问的是"这是不是同一个事件"，而不是"这两句话长得像不像"。

    **回归用例**：`UiSmokeTest.secondIdenticalResultStillShowsTheToast`——
    用空输入连点两次发送（两次结果必然同文案「先写一句要记的账」），
    断言第一次弹、自动收起后第二次仍要弹。**刻意不调模型、不依赖 Key**：
    这条 bug 只在"连着两次"时现形，用例要在任何环境下都跑得到才行。

    实测：instrumented **48 条，0 失败、1 跳过**；JVM 单测仍全绿。

    38. **注释里写通配符 MIME，会把块注释提前闭合**（2026-10-08，编译失败一次）

    给"导入 CSV"写注释时想表达"任意类型"，写了 `{@code */*}` ——
    里面的斜杠星号**直接结束了块注释**，后面的中文注释被当成代码，
    编译器报出一串"非法字符 / 需要 class、interface、enum"。

    这类报错值得记一笔，因为**报错位置（那一行注释）离真正的原因（注释提前闭合）挺远**，
    第一反应容易以为是编码或全角符号问题。
    → 写注释时避开这个字面量（本次改成了文字描述 + 一句"为什么不写它"的说明），
    或写成 `{@code *&#47;*}` 这类转义。

    39. **截图里「日期只在分组标题出现一次」，会让每笔的时间落到今天——而时间错了，重复就判不出来**（2026-10-08 用户实机反馈，同日已修，决策 55）

    用户拿 5 张**内容有重叠**的账单截图（同一段时间连拍的）录账，
    结果有一部分账单进了两次账。现象很具体：重复的两条里，
    一条是图上的原始日期，另一条是**今天**。

    链条是这样接起来的：

    1. 账单列表类截图的分组标题写成 `10月1日 星期四`，下面每条记录**只写时刻**（`18:34 | 转帐-转给某某`）；
    2. 「这个标题管到哪几条记录」模型判不稳（§8-32 早就记过，三条路线都判错过）；
    3. 抄丢日期的那一笔，`RelativeTimeResolver` 只命中时刻 → 日期取参照日 → **今天**；
    4. 去重键的构成是「方向 + 金额 + 发生时间（分钟精度）+ 商户」——发生时间一变，两条键就分道扬镳；
    5. 两条都满足免确认条件（金额小、无存疑）→ **双双直落**，账本里出现两笔。

    → 教训：**去重键里含哪个字段，那个字段的解析错误就会直接变成「去重失效」**。
    所以时间的正确性不只是"时间对不对"，它还是重复能不能被捞出来的前提。

    ✅ **修法（用户拍板，2026-10-08，决策 55）**，四道一起上：
    ① 解析器把「月日」判定提到「周内」之前——`10月1日 星期四` 原先会被 `WEEKDAY`
       抢成「本周四」（它的前缀"这/本/上/下"本来就是可选的），整批日期偏一周。
       **这一条光看现象看不出来，是读正则顺序读出来的**；
    ② 新增 `ImageTranscriptDatePropagator`，把标题上的日期**确定性地下推**到每条含时刻的行
       （同日追加：标题识别得允许行尾那截「出 X 入 Y」统计——用户那张图的记账 App 就是这么排的，
       原先"标题行只许有日期和星期"导致整行匹配失败、**一整天都推不下去**）；
    ③ 截图 prompt 补一条【时间】，要求模型把日期与时刻拼着抄；
    ④ `ConfirmPolicy` 条件 9：截图入口的时间落 `FALLBACK` 时转确认——
       **补不了的那些笔仍要有出口**，否则它们照样静默记成今天、照样重复进账。
    另加一道兜底判重（时间不可信时按「同方向 + 同金额 + 同时分」捞），理由见决策 55。

    **回归用例**：`RelativeTimeResolverTest.monthDayWinsOverWeekdayInBillHeader`、
    `ImageTranscriptDatePropagatorTest`（11 条：单标题补全图 / 多标题只管到下一个 / 无标题原样 /
    「今天便利店」这类商户行不被当标题 / 带「出 X 入 Y」统计的标题行仍要认得出来 /
    带日期的记录行仍不算标题 / 已带日期的不重复补）、
    `ConfirmPolicyTest.imageDraftWithoutTimeConfirms`、
    `DraftRepositoryTest.screenshotDraftWithGuessedDateIsCaughtBySameMoment`。

    实测：JVM 单测 **214 条全绿**、instrumented **59 条 0 失败**（2 跳过）。
    ⚠️ **仍待真机复跑**：拿那 5 张截图再走一遍，看账目时间是否还落本月、
    重叠的那笔是否进确认页（模拟器相册是空的，这条验不了）。

### 多账本类（2026-10-11）

    40. **账本维度复用 `user_id` 之后，凡是"按账目 / 草稿查库"的语句都必须带账本过滤——
    尤其是去重。** `EntryDao` / `DraftDao` / `CategoryDao` / `SettingDao` 里按账目或草稿
    过滤的查询都补上了账本参数；漏一处就出现"账本 A 的账把账本 B 的同额账判成重复"，
    而这种漏法是**静默的**（只是少记一笔、或多问一次），单测、模拟器、Lint 三道防线都看不见。
    最该盯的是这两个：去重键 `countByDedupeKey(key, ledgerId)`、以及"疑似重复"粗筛
    `findByDirectionAndAmount(方向, 金额, ledgerId)`。

    41. **Room 的 `runInTransaction` 不能嵌套。** `LedgerRepository.create` 里
    "写 `t_ledger` 行"与"播种分类"若放进同一个事务，而 `CategorySeeder.seedIfEmpty`
    内部又会开一次事务 → 直接抛异常。**播种、建设置一律放在事务外**（`CategorySeeder`
    自带事务），只把"登记账本行"这一件事包进 `runInTransaction`。

    42. **换了账本，已经在栈里的页面不会自己跟着变。** 各 ViewModel 的查询是构造时
    用"当时的账本"建的，`LiveData` 也不会因为选择变了而重订阅。所以切账本 / 删当前账本之后
    用 `NEW_TASK | CLEAR_TASK` 把任务栈整个换掉（回首页重建），而不是逐个页面去刷新——
    漏一个页面就是"首页换了、账本页还是旧的"这种半新半旧。

    43. **`uiautomator dump` 只包含屏幕上可见的节点。** 它会对滚出屏幕的节点打
    `Skipping invisible child`，所以**不能用"dump 里没有 X"证明"界面上没有 X"**。
    本次就因此误判过一次"新建的账本没出现在列表里"——其实只是它在屏幕外。
    要确认列表内容，要么先滚到那一屏再 dump，要么直接查库。

    44. **PowerShell 下带中文的命令会被吞，`$x` 变量也可能失效**（本项目反复踩到）。
    写含中文的文件名时用 `[char]0x6167 + [char]0x8BB0` 这样拼（本次导出
    `慧记-v1.0-多账本-debug.apk` 就是这么拼的），不要靠 `$var` 中转；
    同理 `findstr` 的 pattern 里放中文会被截断，要匹配中文就先落成文件再用编辑工具看。
