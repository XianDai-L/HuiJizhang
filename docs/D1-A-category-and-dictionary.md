## 1. 预置一级分类

### 1.1 支出（10 项）

```
餐饮 · 交通 · 购物 · 居住 · 通讯 · 娱乐 · 医疗 · 教育 · 人情 · 其他
```

### 1.2 收入（6 项）

```
工资 · 奖金 · 兼职 · 投资 · 红包 · 其他收入
```

`其他收入` 为兜底项。

**收入不设二级分类**（已确认）：收入结构中一级粒度已足够，标准模式下收入账目直接挂一级。
由于账目挂"最末级"（`D1` §6.2），收入挂一级与支出挂二级在数据层完全一致，报表聚合代码不变。

### 1.3 体系约束

一级分类中**禁止出现平级近义项**。「餐饮」与「咖啡」不得并列，「购物」与「日用」不得并列——
这是从分类体系上消除歧义的第一层手段（见 `D1` §6.4）。

### 2.1 边界定义（用于消除歧义）

| 二级 | 包含 | 不包含 |
| --- | --- | --- |
| 餐饮 > 买菜 | 生鲜食材、待加工食品 | 即食食品（→ 零食） |
| 餐饮 > 外卖 | 平台订餐配送 | 到店就餐（→ 聚餐） |
| 餐饮 > 咖啡 | 咖啡店**现制咖啡**（星巴克、瑞幸、库迪、Manner） | 非咖啡饮品（→ 饮品） |
| 餐饮 > 饮品 | 奶茶（蜜雪冰城、茶百道、喜茶）、**瓶装饮料**、果汁 | 咖啡（→ 咖啡） |
| 餐饮 > 零食 | 薯片、坚果、巧克力等**即食食品** | 生鲜食材（→ 买菜）、饮品（→ 饮品） |
| 餐饮 > 聚餐 | **到店线下就餐**（含快餐） | 配送（→ 外卖） |
| 购物 > 日用 | **纸巾、牙线等消耗品**（非食品） | 食品类（→ 餐饮） |
| 通讯 > 话费 / 宽带 | 通信资费 | **会员订阅已删除**（→ 娱乐 > 影音） |
| 娱乐 > 影音 | 腾讯视频、爱奇艺、网易云、B站等订阅 | |

### 2.2 两条体系级调整

**调整一：删除「早餐 / 午餐 / 晚餐」**
按时段分类会与「外卖」冲突（早上点的外卖算哪个？）。改为按**消费形式**分类（外卖 / 买菜 / 聚餐），从体系上消除该类歧义。

**调整二：「咖啡饮品」拆分为「咖啡」+「饮品」**
合并项会产生边界问题（瓶装饮料、奶茶归哪个？）。拆分后判定规则简化为**按商户性质分**：

| 商户性质 | 归类 |
| --- | --- |
| 咖啡店（星巴克、瑞幸、库迪、Manner） | 餐饮 > 咖啡 |
| 奶茶店（蜜雪冰城、茶百道、喜茶、古茗） | 餐饮 > 饮品 |
| 便利店 / 超市买的瓶装饮料 | 餐饮 > 饮品 |

判定**完全确定、不依赖模型**，且与 §3.1 商户映射表一一对应。

### 2.3 关于「聚餐」的语义

按用户确认：**到店吃饭即算「聚餐」**（含独自到店吃快餐），配送上门算「外卖」。
判定只看"到店 / 配送"这一维度，不看人数。

### 3.2 平台型商户（规则映射）

平台型商户**无法硬映射**（淘宝可能是任何东西，美团可能是外卖也可能是买菜）。处理规则：

| 商户 | 有商品名 | 无商品名 |
| --- | --- | --- |
| 淘宝 / 天猫 / 京东 / 拼多多 | 按商品名归二级 | 挂一级「**购物**」 |
| 美团 / 饿了么 | 按订单内容归二级 | 挂一级「**餐饮**」 |
| 盒马 / 永辉 / 沃尔玛 / 华润万家 / 大润发 | 按商品名归二级（蔬菜→餐饮>买菜；纸巾→购物>日用） | 挂一级「**购物**」 |

**设计说明**：
- 平台型无商品名时**不猜二级，只挂一级** —— 因为账目允许挂在末级即一级（见 `D1` §6.2），硬猜二级必然错一半
- **2026-10-02 修订**：原来还要打 `category_swing` 标记去触发确认，现已取消——
  "我们不知道具体买了什么"这件事，用户看分类名就知道，不必再拦一次（HANDOFF 决策 30）
- **超市无商品名归「购物」已确认**（用户：混着就算购物）

**价值说明**：商户映射表的真正价值在**垂直商户**（星巴克、滴滴、腾讯视频），它们占高频场景的多数；平台型只能靠商品名 + 规则兜底。

## 4. 分类的判定顺序（三段确定性判定 + 默认桶）

> **本节已于 2026-10-02 整体改写。** 原版是「四层兜底 + 确定性摇摆判据」——
> 分类字段缺失 / 商户未命中且金额 ≥ 300 元 / 原文含模糊词 / 平台型无商品名 / 模型给 ≥2 候选，
> 满足任一即判 `category_swing` 并推进确认流程。
> 实机验证后被整体删除，理由见 `HANDOFF` 决策 30：**报表按一级分类聚合，二级选错不影响任何统计数字**，
> 那套判据换来的"安全"用户感受不到，付出的"几乎每笔都要点一下确认"感受得很清楚。
> 枚举值 `category_swing` 仍保留在 `ConfidenceFlag` 里，只用于读历史数据。

判定按**越确定越靠前**的顺序，命中即定，全程不反问用户（实现：`CategoryClassifier`）：

| 顺序 | 判据 | 结果 |
| --- | --- | --- |
| 1 | 商户映射表（§3.1 垂直商户） | 命中即定，直接采用 |
| 2 | 平台型商户（§3.2）且无商品名 | 只挂一级，不猜二级 |
| 3 | 模型给出的分类 | 直接采用；**转账**给出「其他」视为"没给" |
| 兜底 | 该方向的默认桶 | 支出/收入 →「其他」/「其他收入」；**转账 →「人情」** |

两点补充：

- **不使用"候选分值分差阈值"** —— 模型自报分值不可靠（与金额校验器同理）。
  模型自报的分值仍存进 `t_draft.category_candidates`，但只作**观测字段**，不作判据（HANDOFF 决策 26）。
- **用户仍可改正分类**：账本里点任意一条账目即可，改正会同时更新账目与关联草稿。

**待办（P2 实测发现，见 `P2-截图实验.md` §3.4）**：模型有"只报一级"的倾向（如转账直接给「人情」），
而工具定义的枚举只列末级路径，于是撞一次 schema 校验、白花一次重试。
可在「枚举补上一级」与「描述里写明必须给末级路径」之间选一个。

## 5. 约数词典

实现形态：外置配置文件 + 纯函数转换器。新增词汇只改配置。

| 口语模式 | 语义 | 展示 | 区间 | 折算值 |
| --- | --- | --- | --- | --- |
| 三十块 | 精确 | `30` | [30,30] | 30 |
| 三十左右 / 差不多三十 / 大概三十 | 约等 | `≈30` | [25,35] | 30 |
| 三十来块 | 约等偏上 | `≈33` | [30,35] | 33 |
| 十几块 | 窄区间 | `10~20` | [10,20] | 15 |
| 五六十块 | 窄区间 | `50~60` | [50,60] | 55 |
| 三四块 | 窄区间 | `3~4` | [3,4] | 3.5 |
| 三百多 | 开下界 | `>300` | (300,400) | 350 |
| 不到三十 | 开上界 | `<30` | [0,30) | 30 |
| 三十以内 / 最多三十 | 闭上界 | `≤30` | [0,30] | 30 |
| 至少三十 / 三十往上 | 开下界无上界 | `≥30` | [30,∞) | **反问** |

### 5.1 区间构造规则（实现依据）

**「来 / 左右」的浮动半径：**

```
spread = min(数量级步长 / 2, N / 6)
  数量级步长 = 10^floor(log10(N 的整数元部分))；不足 10 元时取 1 元

三十左右  → spread = min(10/2, 30/6)    = 5     → [25,35]
三十来块  → spread = 5，折算 1.1N = 33          → [30,35]
六十左右  → spread = min(10/2, 60/6)    = 5     → [55,65]
一百左右  → spread = min(100/2, 100/6)  = 16.66 → [83.34,116.66]
三百左右  → spread = min(100/2, 300/6)  = 50    → [250,350]
```

两个项各自的作用：

- **步长项**：让小额的粒度符合十进制直觉——`三十左右` 是 ±5 元，而不是按比例算出的 ±3 元
- **`N/6` 封顶项**：避免在 10 的整数幂附近区间爆炸——`一百左右` 若纯用步长会得到 [50,150]

**「多 / 几」的步长推进**（与上面不同，推进**完整**一个数量级）：

```
三百多  → 300 + 100 = [300,400]  折算 350
一百多  → 100 + 100 = [100,200]  折算 150
十几    → 10  + 10  = [10,20]    折算 15
```

**双数字区间的统一模型：**`区间 = [d1 × U, d2 × U]`

- 带「十」时 U = 10 × 金额单位：五六十块 → U = 10 元 → [50,60] 元
- 不带「十」时 U = 金额单位：三四块 → U = 1 元 → [3,4] 元；三五毛 → U = 1 角 → [0.3,0.5] 元

### 5.2 折算方向原则

**一律向"高估"方向取整，禁止低估。**

- `<30` 折算 30 是轻微高估，安全（实际 28 时误差 2 元，且更易撞上大额阈值触发确认）
- `≥30` 折算 30 是严重低估（实际可能 3000），**会漏掉确认流程**，因此必须反问

### 5.3 已覆盖的约数词

实现中已覆盖的标记词（见 `ApproxDictionary`）。标记可出现在数字前、数字后，或数字与单位之间（如「三十**来**块」）。

| 位置 | 词 |
| --- | --- |
| 数字前 | `差不多` `大概` `大约` `约` `不到` `不足` `最多` `顶多` `至少` `最少` `起码` |
| 数字后 | `左右` `上下` `来` `出头` `多` `几` `以内` `以下` `以上` `往上` |

匹配按词长降序进行，保证 `差不多` 先于 `多`、`最多` 先于 `多`、`大约` 先于 `约` 被命中。

`[待确认]` 是否补充方言表达：`块把` `块出头` `来块` `约莫`

## 6. 预置分类的初始化时机

| 时机 | 动作 |
| --- | --- |
| 首次启动 | 写入全部系统预置分类（`is_system = 1`），一级 + 二级一次性建好 |
