## 1. 金额口语解析规则

### 1.1 基础规则表

| 口语表达 | 解析结果 | 规则说明 |
| --- | --- | --- |
| 三十五块 | 35 | 十位 + 个位 |
| 三百五 | **350** | 数量级（百/千/万）后省略单位，末位数字降一级 |
| 三百零五 | **305** | 「零」显式占位 |
| 三十块五 | **30.5** | 「块」后跟单个数字 = 角位 |
| 五块二毛 | 5.2 | 「毛」= 「角」 |
| 五块半 | 5.5 | 「半」= 0.5 |
| 五块二毛三分 | 5.23 | 「分」= 分位 |
| 一千五 / 一万五 | 1500 / 15000 | 同「三百五」规则 |

**归一化要求**（ASR 常见误写）：
- 「块」↔「元」，「毛」↔「角」
- ASR 可能输出「快」代替「块」、「圆」代替「元」，需统一归一化

### 1.2 约数词：符号化展示 + 三层分离存储

**设计原则**（用户确认）：约数表达是长尾场景，人类记账很少使用，但必须支持。
因此实现目标为「遇上了不崩、不记错」，**不做自适应学习、不做专项实验、不堆 UI**。
实现形态：**纯配置词典 + 纯函数转换器**，新增词汇只改配置。

#### 1.2.1 三层分离

| 层 | 内容 | 示例 |
| --- | --- | --- |
| 展示层 | 精度符号 + 值 | `30` / `≈30` / `>300` / `50~60` / `<30` |
| 存储层 | 折算值 + 区间边界 | `3000` + `[2500,3500]` |
| 报表层 | 折算值求和 + 浮动提示 | 「本月支出 3,240 元（含 8 笔估算，浮动约 ±85 元）」 |

字段对应：`amount_cents`（折算值，参与统计）+ `amount_lower_cents` / `amount_upper_cents`（区间边界，可空）+ `amount_is_estimated`（估算标记）。

#### 1.2.2 词典与折算规则

| 口语模式 | 语义 | 展示 | 区间 | 折算值 |
| --- | --- | --- | --- | --- |
| 三十块 | 精确 | `30` | [30,30] | 30 |
| 三十左右 / 差不多三十 / 大概三十 | 约等 | `≈30` | [25,35] | 30 |
| 三十来块 | 约等偏上 | `≈33` | [30,35] | 33 |
| 十几块 | 窄区间 | `10~20` | [10,20] | 15 |
| 五六十块 | 窄区间 | `50~60` | [50,60] | 55 |
| 三四块 | 窄区间 | `3~4` | [3,4] | 3.5 |
| 三百多 | 开下界 | `>300` | (300,400) | 350 |
| 不到三十 | 开上界 | `<30` | [0,30) | **30**（取上界）|
| 三十以内 / 最多三十 | 闭上界 | `≤30` | [0,30] | **30**（取上界）|
| 至少三十 / 三十往上 | 开下界无上界 | `≥30` | [30,∞) | **反问** |

**折算方向原则：一律向"高估"方向取整，禁止低估。**

- `<30` 折算 30 是轻微高估，安全——若实际是 28，误差 2 元；且高估更容易撞上大额阈值触发确认
- `≥30` 折算 30 是严重低估（实际可能 3000），会**漏掉确认流程**，因此这类**必须反问**

**反问触发不只看金额大小，还要看"有没有界"**：只有一头有界的表达（`≥30`）无法安全折算。

**配置要求**：区间与折算值必须外置为可配置映射表，不得硬编码于提示词或代码分支。

### 1.3 高危边界

| 风险 | 示例 | 处理策略 |
| --- | --- | --- |
| 「四」/「十」ASR 混淆 | 十四块 ↔ 四十块 | 标 `asr_risk`，见 §2.3，不强制实时反问 |
| 数量 × 单价推理 | 三杯咖啡一杯 15 | 模型推理结果，金额超阈值转确认 |
| 分摊计算 | 四个人 AA 一共 200 | 同上 |
| 多笔一句话 | 早饭 8 块，打车 17，中午请客 230 | 拆分为多张草稿，**拆分场景一律确认** |

## 2. 双通道金额校验器

### 2.1 设计动机

大模型自报的置信度分数不可靠，不能作为"是否存疑"的判据。
替代方案：用**确定性规则**独立重算一遍，与模型输出比对。

### 2.2 工作流程

```
LLM 输出 ──┬─→ amount_cents   （模型算出的金额）
           └─→ amount_raw     （原文片段，如 "三百五"）
                        │
                        ▼
        金额规则校验器（独立代码模块，纯规则，无 LLM）
                        │
        按 §1 规则重算 → 与模型 amount_cents 比对
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   一致：amount_rule_check=pass   不一致：amount_rule_check=fail
          │                           │
          ▼                           ▼
      正常流转                  必然触发反问
```

### 2.3 适用范围与「四/十」风险

- **可校验**：金额（有明确语法，规则可穷举）
- **不可校验**：分类、商户、支付方式（无语法约束，只能靠枚举 + 判定规则）
- 校验器定位：金额防线的哨兵，不是通用准确率方案

「四/十」混淆本质是 **ASR 层错误**，后处理阶段无法"提升识别"，且该错误**静默**（模型解析 40 一路绿灯）。
落地策略（三选一否决「一律反问」）：

1. 语音输入时**显示 ASR 转写文本**（实时字幕），用户当场可发现
2. 带风险条目标记 `confidence_flags += asr_risk`，「最近记账」列表中高亮
3. 原始录音保留，支持回听 + 一键改正

本质：把"实时打断式反问"换成"异步可见 + 可修正"。

## 3. 数据模型：双表

### 3.1 结构决策

**采用双表**（`t_draft` 草稿表 + `t_entry` 账目表），草稿与账本物理分离。

- 优势：账本表只含已确认数据，报表查询无需过滤 `status`，无静默出错风险；实验数据不污染账本
- 代价：核心字段两边各存一份（已接受）

### 3.2 t_draft（草稿表）

```
draft_id            主键
user_id             预留，P1 恒为 1
status              draft | asking | confirmed | posted | discarded | expired
source              voice | image | text_chat | notification | bill_import | manual
created_at / updated_at / posted_at

【交易字段：解析产物，尚未确认】
direction           expense | income | transfer
amount_cents        整数「分」，折算值
amount_lower_cents  区间下界，可空
amount_upper_cents  区间上界，可空
amount_raw          原文片段，如 "三百五"
amount_is_estimated 是否为约数折算值
amount_rule_check   pass | fail | na
occurred_at         交易发生时间
occurred_at_source  explicit | inferred | fallback
category_id         最末级分类 id
root_category_id    所属一级分类 id
category_candidates [{id, score}]
payment_method      枚举：微信 | 支付宝 | 现金 | 银行卡 | 其他
merchant            商户或对方
items               商品明细数组，可空
note                备注

【草稿专属】
raw_input           原始输入文本或 ASR 转写文本
evidence_type       audio | image | text
evidence_ref        音频/图片文件路径
evidence_meta       可选，{bbox, page_no}
batch_id            一次输入拆多笔时共享
split_index
model               模型名 + 版本
clarify_questions   [{field, question, options}]
clarify_rounds      已反问轮数
confidence_flags    枚举标签数组：amount_ambiguous | category_swing
                    | missing_field | split_uncertain | asr_risk
                    （category_swing 已不再产出，仅保留枚举值以读历史数据，见 HANDOFF 决策 30）
dedupe_key          见 §7

【落账后】
entry_id            指向 t_entry，落账成功后写入
```

### 3.3 t_entry（账目表）

```
entry_id            主键
draft_id            溯源，**UNIQUE 约束**（保证幂等）
user_id
direction           expense | income | transfer
amount_cents        整数「分」，绝不用浮点
amount_lower_cents / amount_upper_cents
amount_raw
amount_is_estimated
occurred_at / occurred_at_source
category_id         最末级分类
root_category_id    一级分类
payment_method
merchant / items / note
source              冗余自草稿，便于溯源
created_at
dedupe_key
```

### 3.4 t_category（分类表，统一树结构）

```
category_id         主键
user_id
parent_id           NULL = 一级
level               1 | 2
name
is_system           1 = 系统预置，0 = 用户自定义
is_archived         1 = 停用（不物理删除）
sort_order / icon
```

### 3.5 t_setting（用户设置）

```
user_id
confirm_mode           strict | large | doubtful
large_threshold_cents  默认 30000（300 元）
clarify_max_rounds     默认 3
category_scheme        simple | standard
merchant_map_version
approx_dict_version
```

### 3.6 关键设计要点

- **`amount_cents` 用整数分**：记账铁律，浮点会出现 `0.1+0.2≠0.3`，报表累计误差
- **`occurred_at` 与 `created_at` 必须分开**："昨天下午打车 30" 今晚录入，发生时间落到昨天
- **`raw_input` 必须存**：用户说"这笔记错了"时要能回看原话，也是可解释性基础
- **`evidence_ref` 指向原文件**：录音、截图不立即删除
- **`confidence_flags` 是枚举标签而非分数**：不依赖模型自报置信度
- **`t_entry.draft_id` UNIQUE**：物理保证同一草稿只能入账一次
- **`root_category_id` 在录入时一次算好**：这是分类方案零迁移切换的基础，见 §6

## 4. 草稿状态机

```
              ┌──────────────────────────────────────────┐
              │              收到输入                     │
              └────────────────┬─────────────────────────┘
                               ▼
                        ┌─────────────┐
            ┌───────────│    DRAFT    │◄──────────────┐
            │           └──────┬──────┘               │
            │                  │                      │
   触发确认条件│                  │ 免确认（见 §5.2）      │ 用户回答后
  （档位/校验失败│                  │                      │ 重新解析
   /分类缺失） ▼                  ▼                      │
         ┌───────────┐     ┌─────────────┐              │
         │  ASKING   │     │  CONFIRMED  │              │
         │  反问中    │     └──────┬──────┘              │
         └─────┬─────┘            │ 幂等写入事务          │
               │                  ▼                      │
    用户回答 ───┘            ┌───────────┐               │
    或用户确认 ──────────────►│  POSTED   │ （终态）       │
                            └───────────┘               │
                                                        │
  DRAFT / ASKING ──(用户放弃)──► DISCARDED （终态）        │
  DRAFT / ASKING ──(超时24h)──► EXPIRED   （终态）         │
  ASKING ──(超过3轮)──► 转手动填写表单 ─────────────────────┘
```

### 4.1 状态说明

| 状态 | 含义 | 类型 |
| --- | --- | --- |
| DRAFT | 已解析出草稿，待处理 | 中间态 |
| ASKING | 正在向用户反问 | 中间态 |
| CONFIRMED | 已确认，待写入 | 中间态 |
| POSTED | 已写入账本 | 终态 |
| DISCARDED | 用户主动丢弃 | 终态 |
| EXPIRED | 超时作废 | 终态 |

### 4.2 四个关键约束

1. **用户回答后必须回流到 DRAFT 重新校验，不得直接 CONFIRMED。**
   原因：回答可能引入新信息（回答"是打车"反而暴露支付方式未填）；用户可能语音回答，ASR 仍可能出错。直接确认等于绕过校验器。

2. **反问轮数上限 = 3；超限转手动填写表单。**
   防死循环：避免 AI 反复问同一问题，也避免 `DRAFT → ASKING` 代码层死循环。

3. **POSTED 必须幂等。**
   落账在单事务内完成 + `t_entry.draft_id` UNIQUE 约束。防手抖点两次或网络重试导致重复记账。

4. **多笔拆分只共享 `batch_id`，不共享状态。**
   一次输入拆 3 张草稿，用户可能只确认 2 张。batch 仅是分组标签，每张草稿独立流转。

### 4.3 超时策略

- `DRAFT` / `ASKING` 挂起超过 **24 小时** → 转「待处理」列表，**不删除**
- 待处理条目不再自动流转，由用户下次进 App 自行处理
- 不设"自动作废"期限：数据属于用户，不替他丢弃

## 5. 确认档位与免确认直落

### 5.1 三档设置（用户可选）

| 档位 | 行为 | 触发确认的条件 |
| --- | --- | --- |
| 一 · 每笔确认 | 所有草稿都过确认页 | 全部 |
| 二 · 大额确认 | 小额直接落账 | 金额 ≥ 300 元（可设）**OR** 存疑 |
| 三 · 存疑才确认 | 无风险则直接落账 | 命中 `confidence_flags` **OR** 字段缺失 |

**触发条件为「或」关系**：档位二下若只判金额，AI 把「三百五」记成 305 也不会问。

### 5.2 免确认直落的判定条件

「免确认直落」= 同时满足以下**全部**条件的草稿：

1. `amount_rule_check = pass`（规则重算与模型一致，非"模型自称对"）
2. `amount_is_estimated = false`（非约数）
3. `confidence_flags` 为空（含 `asr_risk`）
4. 必填字段齐全：`amount_cents` / `direction` / `occurred_at` / `category_id` / `payment_method`
5. 分类已定（判定见 §6.4；四条件 2026-10-02 修订，见 HANDOFF 决策 30）
6. 档位二下 `amount_cents` < 大额阈值
7. 去重通过：`dedupe_key` 未命中已有账目
8. **本次输入只拆出这一张草稿**（拆分边界是模型最易出错处）

任一条不满足 → 进入确认流程。

### 5.3 免确认账目的后续处理（澄清）

**免确认直落 = 立刻写入 `t_entry`、立刻计入收支统计**，只是未经用户手动确认。**统计不会少这笔账。**

- 落入「最近自动记账」列表，带**视觉标记**（浅色底/小图标），可快速扫检
- 支持一键撤销、一键改正
- **不设"转正期限"，撤销入口永久保留**（数据属于用户，不给他"过期不能改"的体验）

## 6. 分类方案

### 6.1 两档方案

| 方案 | 可选分类层级 |
| --- | --- |
| 简单 | 仅一级分类 |
| 标准 | 一级 + 二级分类，可选到二级 |

两种方案**共享同一棵分类树**（`t_category`），「简单/标准」只是"是否允许选择二级"的开关。
不存在两套分类表，报表聚合代码也只有一套。

### 6.2 账目挂载规则

**账目一律挂"最末级"**：简单模式下挂一级；标准模式下挂二级（用户也可只选一级）。
`root_category_id` 在录入时一次算好。

### 6.3 双向自由切换（零迁移）

| 场景 | 结果 |
| --- | --- |
| 标准下记「餐饮>咖啡」，切到简单 | 报表按 `root_category_id` 聚合，显示「餐饮」✓ |
| 简单下记「餐饮」，切到标准 | 显示「餐饮」（一级即末级），后续新账目可细分 ✓ |
| 简单下建自定义一级「宠物」，切到标准 | 「宠物」作为一级分类正常显示 ✓ |
| 反复切换 | 账目数据零改动 ✓ |

**升级与降级均已实现且保留**，切换时**不修改任何账目数据**，只改 `t_setting.category_scheme`。

### 6.4 分类的判定顺序（2026-10-07 修订）

判定只剩**两段**，完整说明见 `D1-A` §4：

| 顺序 | 判据 | 结果 |
| --- | --- | --- |
| 1 | 模型给出的分类 | 直接采用；转账给出「其他」视为"没给" |
| 兜底 | 该方向的默认桶 | 支出/收入 →「其他」/「其他收入」；**转账 →「人情」** |

**沿革**：原「四层兜底 + 分类摇摆」2026-10-02 删除（决策 30：报表按一级聚合，
摇摆判据换来的"安全"用户感受不到、"几乎每笔都要点一下确认"却感受得很清楚）；
**商户映射表与平台型规则 2026-10-07 一并删除**（决策 46：截图里出现的商户名不一定与这笔账有关，
命中映射表会把分类定死，连让人改一次的机会都没有）。

用户仍可随时改正分类（账本里点任意一条账目）。

5. **用户习惯学习**：用户改正过的「商户→分类」写入映射表。P1 只做记录，P2 启用。

### 6.5 分类删除策略

**禁止物理删除。** 删除操作改为置 `is_archived = 1`：

- 新建账目时不再出现
- 历史账目仍能正确显示与统计
- 物理删除会导致历史账目变成孤儿，统计直接漏账

## 7. 去重策略

```
dedupe_key = hash(direction + amount_cents + occurred_at(分钟精度) + 归一化 merchant)
```

- 命中已有账目 → 进「疑似重复」队列**由用户选择**
- **绝不自动合并**：连续同额消费（连买两杯一样的咖啡）是真实存在的

| # | 决策项 | 结论 |
